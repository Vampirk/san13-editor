## 1. 개요 및 목적

본 문서는 삼국지 13 PK의 전체 무장 슬롯(ID 0 ~ 1450)과 게임 공식 한글 데이터 파일(`pk_1655.tbl`) 간의 역분석 결과를 수록한 단일 진실 공급원(SSOT) 기술 명세서입니다.

게임 내에서 일부 추가 무장이 실명 대신 임의의 번호(예: `#1242`)로 노출되는 현상을 완벽히 해결하고, 오리지널 역사 무장 700인뿐만 아니라 **PK 공식 추가 사실무장 100인**, **고대무장**, **이벤트 NPC**, **등록 신무장(`editdata_pk.s13`)**에 이르기까지 게임 엔진이 무장 이름을 참조하는 정확한 데이터 구조와 인덱싱 규칙을 영구 보존합니다.

## 2. 게임 원본 바이너리 컨테이너 구조 (`pk_1655.tbl`)

삼국지 13 PK의 모든 텍스트 메시지 및 고유 명사(부락 지명, 명품명, 무장 성명/열전 등)는 `DATA1.S13`의 **Entry 1655**(`pk_1655.tbl`, 708,848 바이트)에 수록되어 있습니다.

### 2.1. 파일 계층 구조
1. **아우터 컨테이너 (Table Header, 0x00 ~ 0x27)**:
   - `0x00`: 포맷 버전 (`0x00000001`)
   - `0x08`: 전체 페이로드 크기 (`0x000AD0E4` = 708,836B)
   - `0x0C`: 섹션 수 (`3`개 섹션)
2. **섹션 1 (`XL13` 서브 컨테이너, 0x28 ~ 0x9FFFF)**:
   - `0x28`: 매직 넘버 (`b"XL\x13\x00"`)
   - `0x34`: 헤더 길이 (`0x00000014` = 20바이트)
   - `0x3C`: 32비트 포인터 배열 시작 지점 (총 26,819개 포인터)
   - **문자열 인코딩**: 한국어 `CP949` (EUC-KR)

### 2.2. 포인터 역참조 및 문자열 해석 공식
포인터 테이블의 각 원소 `pointers[idx]`는 `0x3C`를 기준으로 하는 상대 오프셋입니다.
$$\text{FileOffset}(idx) = \text{0x3C} + \text{pointers}[idx]$$

## 6. 등록 신무장(`editdata_pk.s13`) 저장 구조 — 성명 및 열전

플레이어가 인게임 "등록무장 작성" 기능으로 만든 신무장은 게임 원본 아카이브가 아니라 사용자 PC의 바이너리 파일에 저장되며, 게임 실행 중에는 메모리에 2벌의 사본이 존재합니다. (2026-10-14 실측, 표본: 강월 ID 700)

### 6.1. 파일: `editdata_pk.s13`

- **저장 위치:** `Documents/KoeiTecmo/San13/KR_SAVEDATA/editdata_pk.s13` (Proton: `compatdata/363150/pfx/drive_c/users/steamuser/Documents/...`), 파일 크기 `0x280000` (2.5MB), 파일 매직 `BushouCustom`.
- **블록 마커:** `b"EntryBushou"`는 **블록 전체에 1개만 존재하는 헤더**입니다 (개별 무장마다 반복되지 않음). 같은 파일에 `EntryTactics`(`0x122FE0`, 등록 전법), `EntryItem`(`0x125CE0`, 등록 명품) 블록이 이어집니다.

| 항목 | 값 | 검증 수준 | 비고 |
| :--- | :--- | :---: | :--- |
| 마커 위치 | 파일 `0xF640` | [확정] | |
| 첫 레코드 시작 | `마커 + 0x20` (파일 `0xF660`) | [확정] | |
| 레코드 크기 (Stride) | **`0x464` (1,124 B)** | [확정] | 기본값 레코드 1,000여 개의 반복 주기로 확인 |
| 레코드 ↔ 무장 ID | 레코드 *k* = 무장 ID `700 + k` | [유력] | 표본 1건 (레코드 0 = 강월 700) |

**레코드 내부 레이아웃 (레코드 시작 기준):**

| 오프셋 | 형식 | 필드 | 검증 수준 | 비고 |
| :---: | :--- | :--- | :---: | :--- |
| `+0x000` | CP949 문자열 | 성 (Surname) | [확정] | 강월: `b0ad` = "강" |
| `+0x005` | CP949 문자열 | 명 (Given Name) | [확정] | 강월: `bff9` = "월" |
| `+0x00A ~ +0x034` | - | 미규명 (자(字) 등 추정) | [미확인] | 표본에서 전부 0 |
| **`+0x035`** | **CP949 문자열 (NUL 종료)** | **열전 (列傳, Biography)** | **[확정]** | 강월: 332바이트 "출신과 성씨조차 베일에 쌓인 칠흑의 자객…" |
| `+0x41F ~ +0x463` | 바이너리 | 얼굴/능력치 등 무장 데이터 | [유력] | `+0x426~+0x429` = 통솔/무력/지력/정치 (강월 95/100/90/84 일치) |

- 열전 필드의 최대 길이는 미확정입니다 (다음 필드 `+0x41F`까지 최대 `0x3EA` 바이트 여유). 게임 내 입력 상한 확인 필요.

### 6.2. 게임 메모리 사본 (실행 중)

두 배열 모두 게임 모듈 직후의 정적 데이터 영역(`.bss`)에 있어 **RootBase 상대 오프셋이 실행마다 고정**됩니다. 레코드 앞 `+0x06` 이후 레이아웃은 파일 레코드와 같은 순서(성 → 명 → 열전)입니다.

| 사본 | 위치 (RootBase 기준) | Stride | 개수 | VTable RVA | `+0x04` | 검증 수준 |
| :--- | :--- | :---: | :---: | :---: | :--- | :---: |
| **A. 등록 무장 레지스트리** | `-0x256150` | `0x470` (1,136 B) | 1,049 | `0xD6A478` | `uint16` 무장 ID (700, 701, …) | [확정] |
| **B. 시나리오 등록 무장** | `+0xC2AF34` | `0x424` (1,060 B) | 1,015 | `0xD6C3F8` | `uint16` 인덱스 (0, 1, …) | [확정] |

| 오프셋 (A·B 공통) | 필드 | 검증 수준 |
| :---: | :--- | :---: |
| `+0x00` | VTable | [확정] |
| `+0x04` | 무장 ID(A) / 인덱스(B) | [확정] |
| `+0x06` | 성 (CP949) | [확정] |
| `+0x0B` | 명 (CP949) | [확정] |
| **`+0x3B`** | **열전 (CP949, NUL 종료)** | **[확정]** |

- **미확인:** 인게임 무장 정보창이 A·B 중 어느 사본의 열전을 표시하는지, 그리고 B가 세이브 파일에 저장되는지는 쓰기 실험으로 확인해야 합니다 (`plans/05_BACKLOG.md` RE-02).
- 사본 B는 `OFFSETS.md` 청크 16("등록 무장 & 인연")과 같은 배열이며, 기존에 기록되어 있던 오프셋 `+0xD3DD50`은 실측과 달라 `+0xC2AF34`로 정정했습니다.

### 6.3. 에디터 구현 현황

- [`src/game/OfficerNameTable.cpp`](../../src/game/OfficerNameTable.cpp)의 `LoadCustomOfficerNames()`가 파일을 파싱하여 성명을 700번대 슬롯에 주입합니다.
- **알려진 결함 (BUG-02):** 현재 구현은 `EntryBushou` 마커가 무장마다 있다고 가정하고 마커 위치에서만 성명을 읽으므로, **첫 번째 등록 무장(700)의 이름만 로드**되고 2번째 이후 등록 무장은 이름이 표시되지 않습니다. 열전은 아직 읽지 않습니다.
